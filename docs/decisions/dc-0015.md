# DC-0015 — The repository is the system of record, in OKF

## Context

Requirements, decisions, work items, and tests conventionally live in tools separate from the code:
an issue tracker, a wiki, a test-management system. The result is that the record and the code drift,
and no agent can read the whole picture without four API integrations and four sets of credentials.

## Decision

**This repository is the system of record for the entire software lifecycle.** Every lifecycle
artifact — requirement, epic, story, test case, bug, decision — is an OKF document in `docs/`,
versioned in Git alongside the code it describes.

The storage convention is **OKF (Open Knowledge Format), adopted as-is and not forked**, with a
project SDLC profile layered on top. Both are specified in
[OKF conventions](../guidelines/okf-conventions.md).

The two chains the record must support:

```
Epic → Requirement → User Story → Implementation → Test Case → Verification
Requirement → Test Case → Bug → Fix → Regression Test
```

Requirements may depend on other requirements.

**Features enter through the requirements system first** —
[requirement-first development](../guidelines/requirement-first.md) is the operative rule, and it is
not optional.

## Consequences

- A change to code and the change to its requirement land in the same commit and the same review.
- Traceability is a property of the data, not a report someone assembles.
- Staying OKF-conformant means any other OKF consumer can read this bundle without translation.
- The bundle must stay machine-checkable, which is what [DC-0009](dc-0009.md) exists to do.
- Documentation discipline becomes load-bearing: no duplicated content, stable IDs, links not copies.

## Alternatives considered

- **Jira/Linear + Confluence + a test tool**: four integrations, four auth models, and a record that
  is never in sync with the commit it describes.
- **Issues in the Git forge**: closer, but forge-specific, weakly typed, and with no schema behind the
  relationships.
