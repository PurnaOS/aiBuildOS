# DC-0010 — System Git CLI driven by argv, with worktrees for isolation

## Context

Git is central: it is the storage layer for the record ([DC-0015](dc-0015.md)) and the mechanism by
which parallel agents work without colliding. The product must also behave identically to what the
user sees in their own terminal.

## Decision

Drive the **system `git` CLI**, invoking it with an **argv array** — never a shell string. Isolate
concurrent work in **`git worktree`s**: each agent stream gets its own working directory on its own
branch, sharing one object store.

## Consequences

- The user's Git version, config, hooks, credential helpers, and signing all apply. No reimplementation
  drifts from real Git behaviour.
- argv invocation removes shell-injection as a class of bug: branch names, paths, and messages are
  arguments, never interpolated text.
- Worktrees give parallel agents real filesystem isolation at the cost of disk, and merging becomes an
  explicit, reviewable step rather than an accident.
- Git must be present on the user's machine; the app checks for it at startup.
- **Reads force `core.fsmonitor` off. This is the one deliberate exception to "the user's config
  applies."** See below.

## The `core.fsmonitor` carve-out

`core.fsmonitor` names a program Git *executes* during `git status`. It is read from `.git/config`,
which lives inside the repository directory — cloning does not carry it, but an unpacked archive, a
folder on a shared drive, or any directory handed to the user does.

That matters here because adopting a directory ([RQ-0002](../requirements/rq-0002.md)#AC-5) is a
one-time consent, while the launch page reads every registered project **on every launch,
indefinitely**. Git also runs it silently: measured on Git 2.54.0, an `fsmonitor` program that exits
non-zero still leaves `git status` at exit 0 with empty stderr, so nothing surfaces.

Commands that **read** a repository the application did not create — `status`, `log`, `rev-parse` —
therefore run with `-c core.fsmonitor=`. Commands that **write** — `init`, `add`, `commit` — do not:
they only ever run in a directory the application just created, and they are precisely the operations
this decision wants running under the user's own hooks, signing and credential helpers.

The exception is narrow on purpose. `fsmonitor` is a performance cache, not Git semantics: forcing it
off changes nothing the user sees except the speed of the application's own background reads on a
very large repository. Everything this decision is actually about — hooks, credential helpers,
signing, merge behaviour, the user's Git version — is untouched. Verified by
[TC-0007](../testing/tc-0007.md).

## Alternatives considered

- **`isomorphic-git` / `nodegit`**: no dependency on system Git, but a second implementation of Git
  semantics that will diverge, and no support for the user's hooks and credential helpers.
- **Shelling out with string commands**: injection risk for no gain.
