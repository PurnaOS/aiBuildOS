# DC-0019 — Playbooks are record artifacts, shipped in the project template

## Context

The vision doc promises one-click buttons for the standard SDLC steps, each carrying its own
instructions — and promises that those instructions live *in the project*, "written into a simple
instructions file", so a different AI tool outside this application still follows the same rules.
That rules out an application-side registry: instructions the app holds are instructions only the
app knows.

A playbook needs to be listed, opened, edited, added to, and retired. The application already does
all of that — for record artifacts. A bespoke file format would need its own discovery channel,
its own editor, and its own conventions, all duplicating machinery one directory over.

## Decision

A playbook is an OKF artifact. A `Playbook` type joins the profile — `prefix: PB`,
`dir: playbooks`, states `active | retired`, an optional `harness` field naming the preferred
harness by display name — and the body **is** the instructions, plain Markdown any tool can read.

The standard set (draft requirements, propose a plan, build a story) ships inside the project
scaffold's OKF template, written into every new project at creation. An adopted project without
playbooks can seed the same set on request. The application's buttons are nothing but a filtered
view of the record: `type: Playbook`, `state: active`.

Pressing a button composes the playbook's body with the artifacts the user selected and sends it
through the ordinary session prompt — the transcript shows exactly what was sent, and no channel
exists that the user cannot read.

## Consequences

- Listing, editing, minting and retiring playbooks cost zero new channels — the record machinery
  already does all four.
- The profile grows a type, which is data, not code ([RQ-0003](../requirements/rq-0003.md)
  machinery validates it for free); the conventions' prefix table gains `PB`.
- Playbook files carry OKF common frontmatter, which is heavier than a bare text file — accepted:
  the body stays plain instructions, and the frontmatter is what makes the rest free.
- A project's playbooks travel with the repository; the `harness` field matches by display name
  against local configuration, because harness ids do not travel.
