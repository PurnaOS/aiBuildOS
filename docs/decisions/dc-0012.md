# DC-0012 — Previews via WebContentsView with execa-managed dev servers

## Context

The product shows a live preview of what an agent is building. That means running the target
project's own development server and displaying it inside the app, without the preview being able to
reach into the host application.

## Decision

Run development servers as child processes managed with **`execa`**, and render the result in an
Electron **`WebContentsView`**.

## Consequences

- `WebContentsView` is a separate web contents with its own process and no access to the host
  renderer — the isolation is structural rather than conventional. It is also the supported successor
  to `BrowserView`.
- `execa` gives reliable process trees, signal handling, and cleanup, which matters because an
  orphaned dev server holds a port and confuses the next run.
- Port allocation, readiness detection, and crash surfacing are real problems that arrive with the
  preview requirement; this decision only fixes the mechanism.
- `execa` runs in the main process, so it must stay Node-compatible ([DC-0002](dc-0002.md)) — this is
  exactly the kind of place where reaching for `Bun.spawn` would be tempting and wrong.

## Alternatives considered

- **`<iframe>` in the renderer**: shares the renderer process and its origin privileges.
- **`<webview>` tag**: deprecated in Electron and discouraged.
- **`node:child_process` directly**: workable; `execa` is a thin, well-tested layer over exactly the
  parts (cleanup, signals, process trees) that are easy to get wrong.
