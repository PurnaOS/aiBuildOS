# DC-0021 — Worktree builds: the branch is the binding, and main owns the process

## Context

[DC-0010](dc-0010.md) reserved worktrees for agent isolation; [RQ-0020](../requirements/rq-0020.md)
cashes that in. Three questions had to be answered before code, because each has a wrong answer
that looks fine for a week: where the session↔story binding lives, which checkout owns the
record's process states, and what a commit means in a system that promised nothing commits
without a person asking.

## Decision

**The branch name is the binding.** A build for `ST-0042` runs in a worktree at
`<userData>/worktrees/<project>/<story>` on branch `aibuildos/st-0042`, branched from the main
checkout's current `HEAD`. `git worktree list` *is* the enumeration of running and interrupted
builds; no tracked file records a session id.

**Process state lives in the main checkout only.** Every state flip the application makes —
`ready→queued→building` at start, `building→review` at turn end, the verdicts — is an ordinary
uncommitted edit in the main working tree, exactly like every other guarded save. The application
never writes `docs/` inside a worktree, and the build playbook instructs the agent to leave
`state:` fields alone. A worktree's copy of the record may therefore lag main's uncommitted
flips; nothing reads process state from a worktree, so the lag is invisible by construction.

**Checkpoints are worktree-branch commits; the merge is the person's commit.** At each turn's end
a dirty worktree is committed on its own branch (`checkpoint: <story> turn <n>`) so work survives
an agent that never commits — the user's hooks apply, and a hook's rejection is data on the
build, not a crash. Accepting the build merges the branch into main with `--no-ff`, removes the
worktree, and deletes the branch. The merge commit is app-executed but person-caused: the accept
press is "a person asking", which keeps [RQ-0018](../requirements/rq-0018.md)#AC-5 true. A merge
that cannot land cleanly — including a conflict on an artifact the agent edited despite its
instructions — is reported in Git's words and left for a person; discarding is equally explicit.

**Restart is reconciliation, not resumption.** Builds do not survive the application exiting
(`before-quit` still closes every session); the worktree, its branch, and the record do. On
project open the application prunes stale worktrees and lists survivors: a story at
`building` or `review` with a live worktree can be picked up by a fresh session in that worktree,
prompted from its checkpoints. ACP `session/load` stays deferred.

## Consequences

- Deleting a worktree directory by hand cannot corrupt the record — the record never lived there.
- The main checkout keeps at most one busy session, and the interface caps concurrent builds at
  three; both are ceilings to raise deliberately, not limits discovered under load.
- The `aibuildos/` branch namespace is the application's; a user branch named into it is the one
  way to confuse the enumeration, accepted and documented rather than defended against.
