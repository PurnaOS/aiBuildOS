# DC-0009 — Custom TypeScript knowledge engine over YAML CST

## Context

The OKF bundle in `docs/` is the system of record ([DC-0015](dc-0015.md)). Both humans and agents edit
it. A tool that rewrites a file's untouched frontmatter while changing one field destroys the diff,
and a diff nobody can read is a review nobody does.

## Decision

Build a **custom TypeScript knowledge engine** (`packages/knowledge-engine`) rather than adopting a
generic document store. Three commitments:

1. **YAML CST round-trip.** Edits operate on the `yaml` package's **CST layer**, mutating the targeted
   token in place, so everything else is reproduced byte for byte. The higher-level `Document` API
   re-stringifies from a resolved node tree and reformats comment spacing and flow-collection padding
   it never touched — confirmed against hand-formatted fixtures in the predecessor project.
2. **Zod for schema validation**, since the schemas are also the IPC contracts' vocabulary.
3. **Ajv as an escape hatch.** The profile dialect carries a `json_schema` key
   ([conventions §6](../guidelines/okf-conventions.md#6-the-profile--types-are-data)) for constraints
   the friendly dialect cannot express, validated with Ajv. This keeps the dialect small instead of
   letting it grow into a general-purpose schema language.

A rule/graph engine sits on top: artifacts form a directed graph, and rules are evaluated over it to
produce findings.

## Consequences

- Byte-fidelity is a testable property, and must be tested — round-trip fixtures are the guard.
- This bootstrap ships the *boundary* only: parse, validate, graph. CST-based editing, the rule
  engine, gates, and Ajv wiring each arrive with their own requirement.

## Alternatives considered

- **`gray-matter` + `js-yaml`**: reformats on write. Disqualifying.
- **A database with Markdown export**: breaks "the repo is the record" — Git stops being the source of
  truth the moment the database is.
