# DC-0029 — Hands-off maps to accept-edits, never to bypass

## Context

[RQ-0050](../requirements/rq-0050.md) maps each supervision level to a permission option the
harness advertises. Every harness that offers such an option offers a most-permissive value —
`bypassPermissions` for the Claude agent, `agent-full-access` for Codex — and mapping *hands-off*
to it is the obvious reading of the words.

It is the wrong reading. [RQ-0022](../requirements/rq-0022.md)#AC-3 does not say the agent stops
asking at hands-off; it says a request "is answered with the agent's own allow option, and the
transcript records the answer as automatic — **visible, never silent**." Hands-off is *the
application answering, in the open* — not the question disappearing.

## Decision

**Hands-off maps to the accept-edits class of option** — `acceptEdits` for the Claude agent,
`agent` for Codex — **and never to the bypass class.**

The bypass values delete the permission request upstream, inside the harness. Nothing reaches the
application, so there is nothing to answer and nothing to show: RQ-0022#AC-3's record does not
merely become inconvenient, it ceases to exist. Two further floors go with it — the application
emits its permission event *before* it auto-answers, precisely so the card shows what was allowed
and that no person allowed it; and at hands-off with no allow option offered, the answer is
`null` and the request still blocks for a person. Bypass removes that last floor silently.

**A harness advertising no permission option ships unmapped.** Gemini's CLI offers no session
config options at all, so it carries no mapping and says so — absent is not the same as offering
nothing, the distinction the agent-settings surface already draws.

### The gap this leaves, stated rather than implied

`acceptEdits` silences the *edit* permission inside the harness. Those edits therefore do **not**
reach the transcript as automatic answers, so "hands-off preserves every permission on the
transcript" is false in exactly this one way. It is accepted because an edit is already visible
twice over — the tool-call card as it happens, and the diff at review — while a command is
visible nowhere else, and commands keep asking under `acceptEdits`. Anyone reading RQ-0022#AC-3
and expecting edit permissions in the transcript at hands-off should read this paragraph instead
of finding the gap themselves.

## Consequences

- The mapping values are per-harness data on the record ([RQ-0050](../requirements/rq-0050.md)
  #AC-2), so this decision constrains what is *prefilled*, not what a user may set. Someone who
  deliberately maps hands-off to bypass gets bypass — and loses the transcript record, knowingly.
- Harness option vocabularies drift; the shipped presets are read from the published agent
  bundles and carry a `ponytail:` marker naming that staleness ceiling.
- If a harness ever offers a value that is *both* fully permissive and still emits requests, this
  decision should be revisited — the objection is to the request vanishing, not to permissiveness.

## Alternatives considered

- **Hands-off → bypass**, the literal reading: rejected. It contradicts RQ-0022#AC-3 outright and
  removes the no-allow-option floor without saying so.
- **Leave hands-off unmapped everywhere** and keep supervision purely app-side: rejected. It
  would make RQ-0050 pointless for the level where reaching the harness matters most.
- **Narrow RQ-0022#AC-3** so bypass becomes legal: rejected. The visibility of an automatic
  answer is the thing that makes hands-off safe to offer at all.
