# DC-0028 — Harness capabilities ride ACP extension points

## Context

[EP-0016](../epics/ep-0016.md) wants capabilities today's harnesses expose only outside ACP's
baseline — schema-conforming output above all. The non-negotiable stands: ACP is the only door to
AI ([DC-0007](dc-0007.md)). The question is whether that door has room, and the spec answers
yes — verified against agentclientprotocol.com on 2026-08-21:

- All protocol types carry a `_meta` field for implementation-defined data; custom fields at the
  root of a specification type are **MUST NOT**.
- Method names beginning with `_` are reserved for custom extensions, and implementations
  **SHOULD** advertise extension support through the `_meta` field of capability objects at
  initialization.
- Permission behaviour needs no extension at all: **Session Config Options** are standard —
  `configOptions` returned at `session/new`, changed via `session/set_config_option`, pushed via
  `config_option_update`, with the spec's own example a mode selector that "controls how the agent
  requests permission". The older Session Modes API carries a removal notice; nothing new builds
  on it.

## Decision

**Extensions ride the spec's own extension points, negotiated per agent.** Anything beyond the
ACP baseline — typed plan and verdict outputs first ([RQ-0052](../requirements/rq-0052.md)) — is
carried in `_meta` fields or underscore-prefixed custom methods, advertised via `_meta` capability
entries at initialization, implemented inside `packages/acp`. An agent that doesn't advertise the
extension gets the baseline behaviour; degraded is a first-class path, exercised by the stub agent
in CI.

**Permission mapping uses standard config options, never the deprecated modes API**
([RQ-0050](../requirements/rq-0050.md)): the supervision mapping targets `configOptions` /
`session/set_config_option`, and listens for `config_option_update`.

## Consequences

- The per-harness knowledge (which extension, which option ids) lives in agent descriptors as
  data — the same place harness identity already lives.
- Our extensions are candidate proposals for upstream ACP, the same posture
  [DC-0020](dc-0020.md) took for structured asks: convention now, standard when the protocol
  catches up, delete the convention then.
- The stub agent grows extension fixtures so both the extended and baseline paths stay tested
  without a live model.
- Two doors stay closed: no vendor SDK beside ACP, and no forked protocol types.

## Alternatives considered

- **An Agent SDK sidecar for the harness that has one**: rejected. It breaks the non-negotiable,
  special-cases one vendor, and every capability it would buy is reachable through `_meta` for a
  harness willing to advertise it.
- **Strict baseline ACP only**: rejected. It leaves typed outputs unreachable indefinitely for no
  principle the spec itself holds — the spec *designed* the extension points.
- **Forking protocol types**: forbidden by the spec (**MUST NOT** add root fields) and pointless
  given `_meta` exists.
