# DC-0020 — Structured asks ride a fenced-block convention until ACP elicitation is real

## Context

The vision doc wants the agent to ask one clear question at a time with tappable options. ACP has
no generic ask-with-options: `session/request_permission` originates in the harness's own tool
gating and cannot carry an arbitrary question, and the SDK's `elicitation/create` — which is
exactly this — is marked experimental, with no harness known to ship it. An app-served MCP
`ask_user` tool is protocol-possible but the largest option, for the same model-obedience
fragility a prompt convention has.

## Decision

A playbook instructs the agent to pose each question as one fenced block, info string
`aibuildos-question`, containing `{ question, options: [{ id, label }], allowFreeText }`, then end
its turn. The renderer detects the fence on a **completed** message — partial fences are noise —
and renders a card offering exactly those options; a tap sends the answer back as an ordinary
prompt. Malformed structure degrades to visible text, never to an error: the fence simply renders
as what it is, and the person types.

When a harness ships elicitation, the wiring mirrors the existing permission flow — advertise the
capability, one request handler, one bridge event — and lands in **the same card**. The card is
the seam; the wire behind it is replaceable.

## Consequences

- Zero new IPC and zero main-process code now; the whole mechanism is renderer detection plus
  playbook prose, and it works with every harness including the CI stub.
- The convention is honest about being one: a model can ignore it, and the degradation path is
  the conversation everyone already has.
- Elicitation adoption later is roughly a day, not a redesign, because nothing but the card's
  data source changes.
