# DC-0025 — A sprint is a branch with its own worktree; -- binds its stories

## Context

[RQ-0035](../requirements/rq-0035.md) makes a batch of stories a first-class thing that builds in
parallel and lands together. [DC-0021](dc-0021.md) already settled the single-story shape — the
branch is the binding, main owns the process states. A sprint stresses each of those answers:
where story merges land, how a story branch names its sprint, and whose checkout carries the
record's flips.

## Decision

**A sprint is a branch — with its own worktree.** Starting sprint `SP-0001` creates
`aibuildos/sp-0001` and a worktree checked out on it. The worktree is not a convenience: story
merges must land *on the sprint branch*, and git cannot merge into a branch no checkout has out.
The sprint worktree is where its stories' accepted work accumulates.

**`--` is the story binding.** A story building inside the sprint takes branch
`aibuildos/sp-0001--st-0049`, branched **from** the sprint branch. Nesting as
`aibuildos/sp-0001/st-0049` is impossible — refs are files, so `aibuildos/sp-0001` existing as a
branch forbids anything nested beneath it. The doubled hyphen cannot appear in an ID, so parsing
is unambiguous, and DC-0021's property extends: the sprint, its stories, and their bases all
survive restart with **no tracked file** — the branch names are the whole record.

**Record flips stay in the main checkout.** Same rule as DC-0021, and the ancestry argument for
why it stays safe at sprint scale: story checkpoints never touch `docs/` (the build playbook
forbids it, and the application only ever flips states in main's working tree), so every commit on
the sprint branch leaves `docs/` untouched — the sprint branch's `docs/` remains **byte-identical
to its base**. When the sprint merges into main, main is a descendant of that base and its own
`docs/` edits are therefore the only ones in play: the merge cannot conflict on the record. And
because the flips live in main, the boards read them live — a sprint story showing `building` or
`review` is always true, never hidden on a branch the boards cannot see.

**Finishing is `--no-ff`, and never over live stories.** `sprint:merge` lands the sprint branch on
main as one merge commit; both merge and discard refuse with `stories_live` while any
`sp-0001--*` worktree exists — a sprint cannot be closed out from under a build.

## Consequences

- Two layers of the same shape: story → sprint mirrors sprint → main, each an explicit `--no-ff`
  merge a person caused.
- One more worktree per running sprint, on top of the per-story ones; disk is the cost of merges
  having somewhere to land.
- The `aibuildos/` namespace now encodes structure; a user hand-naming a branch with `--` into it
  remains the documented way to confuse the enumeration, as in DC-0021.

## Alternatives considered

- **Reusing Epic as the sprint**: rejected by the owner. An epic is scope — what the stories are
  for; a sprint is a batch in time. Conflating them makes one artifact answer two unrelated
  questions badly, so Sprint enters the profile as its own type.
- **`/`-nested story branches** (`aibuildos/sp-0001/st-0049`): rejected. Git's ref namespace
  forbids nesting under an existing branch name; the `--` separator gives the same readability
  without fighting the ref store.
- **A tracked file recording sprint membership**: rejected. A file is a second source of truth
  that can drift from the branches; DC-0021 already proved the branch name alone survives restart.
- **Flipping record states on the sprint branch**: rejected. The boards would lie about sprint
  stories until merge, and the sprint's `docs/` would collide with main's at landing — the exact
  conflict the byte-identical invariant rules out.
