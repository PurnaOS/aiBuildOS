# RQ-0048 — A requirement can carry a design

Between "the requirement is clear" and "the plan is approved" there is nothing to look at. For
anything with a face, that is where misunderstandings hide: the owner imagined one screen, the
agent built another, and the mistake surfaces after the build instead of before it. A design is
the record artifact that closes the gap — a high-fidelity mockup the agent proposes *from* the
requirement, rendered in the preview surface the workspace already has ([RQ-0025](rq-0025.md)),
reviewed and approved beside the requirement it visualises, before anything is scheduled.

The `Design` type enters the profile with this requirement ([the Design
profile](../profile/design.md)) — the Sprint precedent, again.

## Acceptance criteria

- [AC-1] A design is a record artifact in `docs/designs/` tracing to at least one requirement,
  walking `draft → review → approved` like any other artifact.
- [AC-2] From a draft requirement, the agent proposes a design: a rendered mockup beside the
  requirement, in the workspace — not a paragraph describing one.
- [AC-3] The owner approves or asks for changes right there; approving is a state change on the
  design, and the revise loop mirrors plan-approve.
- [AC-4] Planning a requirement that has an approved design hands the design to the plan and the
  build — the story's agent sees what was approved, not a retelling.
- [AC-5] A requirement without a design plans and builds exactly as today. The design phase is
  per-requirement and optional; nothing gains a mandatory step.
