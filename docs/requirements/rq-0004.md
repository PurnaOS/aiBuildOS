# RQ-0004 — A project opens into a workspace where an agent works on it over ACP

[RQ-0002](rq-0002.md) gave the product a subject: a project is created or adopted, and opening one
reports its branch, its working tree and its record. That view is a **status page**. Nothing happens
in it, and [RQ-0001](rq-0001.md)'s harness can still only be asked one fixed question and then killed.

This is where the two meet. A project must open into a place where a coding agent does real work on
the repository, and where the person driving it can see what it is doing, answer what it asks, steer
what it uses, and read both the code and the record beside the conversation.

The arrangement is deliberate and is the product's argument. Other tools organise around a workspace
or a branch. Here the **record is the left rail and the files are the right rail**, because a
requirement is what work is *for* and a file is where it *lands* — and this repository already keeps
its whole lifecycle in Git ([DC-0015](../decisions/dc-0015.md)) precisely so that both can be shown.

An agent is not only a text generator. It asks for permission, it may ask for structured input, it may
need to be logged in, and it exposes its own modes, models and effort levels. Every one of those is
**advertised by the agent** ([DC-0007](../decisions/dc-0007.md)) — so the interface renders what the
agent offers and invents nothing. A hardcoded model list, or an Allow/Deny pair the agent never sent,
would be this requirement failing.

Editing what the workspace shows is [RQ-0005](rq-0005.md); it depends on this one. Running an agent
against several branches at once, staging and committing from the interface, brokering filesystem and
terminal access on the agent's behalf, and persisting a transcript across restarts are all out of
scope here and named in [EP-0004](../epics/ep-0004.md).

## Acceptance criteria

- [AC-1] Opening a project shows a workspace with the record on the left, the conversation in the
  centre and the project's files on the right. Both side panels can be resized and collapsed, and
  their sizes survive a restart.
- [AC-2] The centre is a tabbed surface. The conversation is the first tab and cannot be closed;
  everything opened from either side panel opens as a further tab beside it.
- [AC-3] The user can send a message to the configured harness and receive the agent's reply streamed
  into the conversation as it arrives, not on completion.
- [AC-4] A session stays open across messages: a second message continues the same conversation
  without respawning the agent.
- [AC-5] The agent's intermediate reasoning is shown, distinguishable from its answer, and collapsed
  by default.
- [AC-6] Each tool the agent uses appears as its own entry reporting what it is, what it is acting on,
  and whether it is pending, running, complete or failed. Status is conveyed in words, never by colour
  alone.
- [AC-7] A file change made by the agent is shown as a diff, with the path and the number of lines
  added and removed.
- [AC-8] When the agent reports a plan, the workspace shows it as a list of steps with the completed
  ones marked, and replaces it wholesale each time the agent resends it.
- [AC-9] When the agent asks permission to act, the workspace blocks on that question and offers
  exactly the options the agent supplied, in the agent's own wording.
- [AC-10] When the agent cannot start because it is not authenticated, the workspace reports that as a
  distinct, non-fatal outcome and offers the authentication methods the agent advertised.
- [AC-11] The user can cancel a turn in progress. Cancelling leaves any outstanding permission
  question answered as cancelled, continues to accept the agent's remaining updates, and reports the
  turn as cancelled rather than as failed.
- [AC-12] The modes, models and effort settings a session offers are read from the agent, shown as
  controls, and changed through it. A setting the agent does not offer is absent, not empty or
  disabled, and a change the agent reports independently is reflected without the user acting.
- [AC-13] The commands a session advertises are offered in the composer, and what is sent to the agent
  is what the conversation shows.
- [AC-14] The left panel lists the project's record grouped by artifact type, showing each artifact's
  ID, title and state, and the work and verification linked to a requirement. It reads links in one
  direction only and derives the reverse.
- [AC-15] The right panel shows the project's files as a tree and, on a second tab, its Git changes
  grouped by staged, unstaged and untracked, with recent history. Selecting a change opens its diff.
- [AC-16] The file tree reflects Git's view of each path, and does not read the whole working tree to
  display one directory.
- [AC-17] Every failure is reported in words, distinguishing at least: no harness configured, the
  agent command not being found, the agent exiting before or during a session, a protocol error, and
  the project directory having been removed.
- [AC-18] Nothing in the renderer speaks the agent's wire protocol, holds a model client, or reads the
  record's files directly.
