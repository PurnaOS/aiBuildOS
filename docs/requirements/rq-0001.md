# RQ-0001 — Coding harnesses are configured in the app and connected over ACP

aiBuildOS drives coding agents, and [DC-0007](../decisions/dc-0007.md) makes ACP the only door to
them: an agent is a stdio child process speaking JSON-RPC, and an adapter is configuration, not code.
Nothing in the product acts on that yet.

A **harness** is one such configured agent — a display name, an executable, its arguments, and
optionally the directory to run it in. The user owns that list: they add harnesses, edit them, remove
them, and prove one works before trusting it with their repository.

Testing a harness performs a **full round trip** — handshake, session, prompt, reply — because the
question the user is really asking is "will this actually answer me?", and a handshake alone cannot
answer it. Automated verification uses the scripted stub agent, never a live model
([DC-0013](../decisions/dc-0013.md)).

Credentials are out of scope here. Harnesses inherit the application's environment, so an agent CLI
already authenticated on the machine works unchanged. Per-harness secrets belong to
[DC-0011](../decisions/dc-0011.md) and arrive with their own requirement.

## Acceptance criteria

- [AC-1] A harness is stored configuration — a display name, an executable command, its arguments and
  an optional working directory — and survives an application restart.
- [AC-2] Settings lists every configured harness and supports adding, editing and removing one.
- [AC-3] Adding a harness offers presets for the harnesses aiBuildOS ships support for, prefilling the
  command and arguments, editable before saving.
- [AC-4] When the application opens with no harness configured, it prompts the user to attach one. The
  prompt does not appear once at least one harness exists.
- [AC-5] Testing a harness spawns it as a stdio child process, performs the ACP `initialize`
  handshake, opens a session, sends a fixed prompt, and reports the agent's reply.
- [AC-6] A successful test reports the negotiated protocol version, the agent's name and version, its
  advertised capabilities and its authentication methods. A field the agent does not advertise is
  reported as not advertised, not as a failure.
- [AC-7] A failed test reports which stage failed and why, distinguishing at least: the command not
  being found, the working directory not existing, the process exiting before the handshake, no
  response within the timeout, and a protocol error. An agent requiring authentication is a distinct,
  non-fatal outcome.
- [AC-8] Every test terminates the agent process on every path — including an agent launched through
  a wrapper such as `npx`, where the agent is not the process aiBuildOS spawned.
- [AC-9] Harness configuration is never overwritten from a read that failed. A file that exists but
  cannot be read as configuration blocks writes and says so, rather than being replaced.
- [AC-10] A configuration or test operation that fails reports the failure in the interface. No
  failure is silent.
