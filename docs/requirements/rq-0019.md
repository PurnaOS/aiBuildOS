# RQ-0019 — The project's checks run from the workspace, and the story shows the outcome

Review reads diffs against criteria and takes the code's word for the rest. The vision doc's step
9 wants evidence: the project's own checks — its tests, its linters, whatever it declares — run
from the workspace, watched as they run, their outcome standing beside the story they judge.

The checks belong to the project, not the application, and they live where everything else the
project declares lives: in the record. A playbook of checks — fenced command blocks in an
ordinary readable artifact — is a file a person can read, an agent can follow, and the
application can run, without a configuration format existing anywhere. Exit codes are the whole
verdict; parsing reporter output is a fidelity this requirement does not buy.

The workspace never decides to run them. A person does, or a playbook's own instructions tell the
agent to — the application is the hands, not the judgement. Refusing a state flip on a red check
is the gates feature, deferred by name; this requirement makes the truth visible without blocking
anyone on it.

## Acceptance criteria

- [AC-1] The project declares its checks as commands in a record artifact; the workspace lists
  them from the record alone, and a project declaring none offers nothing.
- [AC-2] A person can run the checks from the workspace; each command runs as a child process in
  main, and its output is visible as it arrives.
- [AC-3] Each command's outcome — pass, fail, or could-not-run — is reported in words, the exit
  code the only verdict.
- [AC-4] A story under review shows the latest run's outcome beside it, and a failing run can be
  handed to the agent with the failure as context, in one act.
- [AC-5] Closing the application leaves no check process running.
