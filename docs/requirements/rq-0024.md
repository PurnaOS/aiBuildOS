# RQ-0024 — When a requirement changes, what it touches is found and re-planned

The vision doc's step 11: minds change, and the system works out what that touches instead of
letting it quietly fall out of date. The machinery is the graph the record already is — a
requirement's implementing stories and verifying tests are derived links, and "what does this
change affect" is a read, not a bookkeeping duty.

Like [RQ-0007](rq-0007.md) before it, this stands outside the epic structure: the epic it
belongs to by theme ([EP-0005](../epics/ep-0005.md)) closed with its original scope, and a
one-requirement epic would be ceremony.

## Acceptance criteria

- [AC-1] After a requirement past `ready` is edited, the workspace shows what implements and
  verifies it, each with its current state.
- [AC-2] That view tells work already done apart from work in progress and from verification.
- [AC-3] A re-plan can be started from it with the changed requirement as context, through the
  plan playbook; the proposal arrives as draft artifacts exactly as a first plan does.
- [AC-4] Criteria appended to a verified requirement leave existing numbers and their
  verification intact.
- [AC-5] Nothing is demoted automatically; every state change remains a deliberate act.
