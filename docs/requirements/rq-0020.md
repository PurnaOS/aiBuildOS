# RQ-0020 — A build runs in its own worktree while the workspace stays free

Building today borrows the main working tree, so while an agent builds, the workspace is half
yours: your own edits and the agent's land in one place, and a second build is out of the
question. [DC-0010](../decisions/dc-0010.md) reserved the answer years of tooling converged on —
a worktree per stream — and [DC-0021](../decisions/dc-0021.md) settles how it works here: the
branch is the binding, the main checkout owns every process state, checkpoints save work the
agent never committed, and the merge that lands it all is the person's accept.

## Acceptance criteria

- [AC-1] Starting a build can place it in a fresh worktree on its own `aibuildos/` branch; while
  it builds, the main workspace stays fully usable — editing, planning, reviewing.
- [AC-2] The building agent's activity is watchable live, and switchable away from without
  stopping it.
- [AC-3] Each turn's end checkpoints a dirty worktree on its branch; a hook rejecting the
  checkpoint is reported on the build, and the work stays in the worktree.
- [AC-4] Review of a worktree build shows the branch's changes; accepting merges `--no-ff` into
  main, removes the worktree and deletes the branch — the person's accept is the commit.
- [AC-5] A merge that cannot land cleanly is reported in Git's words and left for a person, with
  discarding equally explicit; nothing is force-resolved.
- [AC-6] A build does not survive the application exiting; the worktree, branch and record do,
  and reopening the project lists them for a fresh session to pick up.
