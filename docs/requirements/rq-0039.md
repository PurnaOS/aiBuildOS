# RQ-0039 — Playbooks run in the background

A long planning run blocks the conversation: the owner asks for a plan, then waits, unable to talk
about anything else until the turn ends. Playbooks should run beside the chat, not inside it. The
`session:start` request gains `background: {label}`; the registry stores the label on `Held`; and
**`busyCount()`** — a session is busy when `storyId ≠ null` or `label ≠ null` — becomes the single
cap check shared with worktree builds, with `CONCURRENCY_CAP = 3` moved next to it. Any active
playbook may run in the background; there is no whitelist.

The renderer composes the prompt with the existing `compose()`, starts the session, and
fire-and-forgets `session:prompt` — the WorkBoard worktree-prompt precedent, not a new pipeline.
The run gets a dock row and a `session:<id>` tab; the main chat and its CopilotKit pipeline are
untouched. Turn-end needs no wiring at all: the watcher ([RQ-0026](rq-0026.md)'s mechanism) sees
whatever the run writes. The renderer affordances — composer `+` menu entries and PlanSurface's
plan button — target the redesigned homes, so this requirement's surface lands after the redesign
slot.

## Acceptance criteria

- [AC-1] Any active playbook can be started as a background session carrying a label, and the main
  chat stays interactive for the whole run.
- [AC-2] Background runs and worktree builds share one cap through a single `busyCount()`: with
  three busy sessions of any mix, starting a fourth is refused.
- [AC-3] A background run appears as a dock row, and its transcript opens as a `session:<id>` tab.
- [AC-4] Artifacts a background run writes appear in the workspace via the watcher, with no
  turn-end wiring added for background sessions.
- [AC-5] Starting and finishing a background run changes nothing in the main chat pipeline.
