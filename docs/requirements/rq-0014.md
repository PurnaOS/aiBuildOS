# RQ-0014 — Picked requirements become a proposed plan, and approving it is a state change

The vision doc's steps 4 to 6: pick what to build, see a plan, shape it, say go. The thesis is
that a plan is not a new kind of thing. A proposal is draft Story and TestCase artifacts written
into the record by the agent; the plan view is a *derived* gathering of everything at `draft`,
grouped by the requirement it implements; and approval is nothing but state flips, made one save
at a time through the door [RQ-0010](rq-0010.md) guards. The workspace holds no plan of its own —
close the application mid-review and the proposal is still there, because it is files.

Approval is also where the traceability chain gets enforced, for free: the profile already says
a story at `ready` must implement a requirement and carry a verifying test. A proposal that
skipped the tests cannot be approved — not as a feature of the plan view, but because the
record's own rules refuse the flip.

## Acceptance criteria

- [AC-1] Ready requirements can be picked — one, several, or all — and the plan playbook started
  with exactly those as context.
- [AC-2] The proposal is draft Story and TestCase artifacts in the record; the workspace holds no
  plan state of its own.
- [AC-3] Draft work is gathered into one plan view, grouped by the requirement it implements,
  ordered so reading order is build order; it survives restarts because it is derived from files.
- [AC-4] Any draft in the plan can be edited or retired before approval, with the editing the
  workspace already has.
- [AC-5] Approving flips each story `draft → ready` and each test case `draft → active`; every
  flip goes through the same guarded save path, one artifact at a time.
- [AC-6] A story that no test case verifies cannot be approved; the refusal stands on the story,
  in the record's own words, and the rest of the plan is not held hostage by it.
- [AC-7] A draft the validator rejects is marked in the plan view and cannot be approved until
  fixed.
