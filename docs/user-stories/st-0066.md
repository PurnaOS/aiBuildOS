# ST-0066 — Scaffolding writes the harness's guardrails

*As an owner initializing a project, I want the record's hard rules to be enforced by the
harness itself — files in my codebase from day one — not just requested in prose.*

Two seams, both existing: `bundleFiles()`/`seedBundle` in `apps/desktop/src/main/scaffold.ts` for
created projects, and the seed-into-existing routine in `playbooks.ts` for adopted ones. Both
grow a per-harness hook layer: for a harness with file-side hook support (Claude Code:
`.claude/settings.json`), write PreToolUse guardrails denying edits to `state:` fields and
protected record files — the rules AGENTS.md states as prose today. Two known traps from
reconnaissance: the template glob is `**/*.md` only (a JSON hook file will silently not ship —
widen it), and `seedPlaybooks` refuses projects that already have PB-* files (the "gains them
next time" path needs its own guard, per-file like the AGENTS.md rule, never overwriting).
Scaffolded hooks must not block the app's own checkpoints, and activation rides the harness's
trust flow.

## Acceptance criteria

- [AC-1] Creating a project writes the guardrail hook files for the configured harness beside
  AGENTS.md/CLAUDE.md; adopting or re-seeding an existing project adds missing ones and never
  overwrites present ones.
- [AC-2] The written hook config is valid for its harness (parses, matches the harness's
  documented hook schema) and denies `state:` edits and protected-file writes.
- [AC-3] A harness with no hook support scaffolds exactly as today — instructions only, no error.
- [AC-4] The app's own checkpoint commits succeed in a project carrying the scaffolded hooks.
