# ST-0010 — Answer what the agent asks, and steer what it uses

*As someone responsible for what an agent does to my repository, I want to be asked before it acts,
and to choose which model and how much effort it uses, so that I am steering rather than watching.*

Serves [RQ-0004](../requirements/rq-0004.md) criteria AC-9, AC-10, AC-12 and AC-13.

One rule governs all of it: **the agent advertises what is on offer and the interface renders exactly
that.** The buttons on a permission prompt are the agent's. The models in the picker are the agent's.
An agent that offers no modes shows no mode control — not an empty one.

The probe declines every permission automatically, which is right for a probe and wrong for a person.

## Acceptance criteria

- [AC-1] A permission request stops the turn and is shown with one control per option the agent sent,
  labelled in the agent's own words.
- [AC-2] The user's choice is returned to the agent, and the turn continues.
- [AC-3] Cancelling while a permission request is open answers it as cancelled, as the protocol
  requires.
- [AC-4] A session that cannot start because the agent is not authenticated is reported as its own
  outcome, offering the methods the agent advertised, and is not reported as a crash.
- [AC-5] The modes, models and effort settings a session advertises are shown as controls; changing
  one tells the agent, and the control reflects what the agent confirms rather than what was clicked.
- [AC-6] A control the agent does not advertise is absent. A category the protocol does not name is
  still shown, under the agent's own label.
- [AC-7] The commands a session advertises are offered in the composer, and what is sent is what the
  conversation shows.
- [AC-8] Structured-input requests have a place in the design and are not implemented: the client
  advertises no capability for them, and the protocol calls them unstable.
