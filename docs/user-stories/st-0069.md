# ST-0069 — Harness commands join the composer

*As an owner, I want what the harness can do listed where I compose — beside my playbooks, in
the harness's own words — not hidden in a chip.*

The transport is done: `available_commands_update` flows bridge → `Controls` cache →
`session:controls`, live and wholesale-replaced. This story is the surface: the composer home
([RQ-0043](../requirements/rq-0043.md)'s `+` menu, built by the parallel round-three slot) gains
an origin-grouped Commands section fed by a session-keyed `useSyncExternalStore` store (the
`toolCall.ts` pattern — never the UI-only zustand store, per DC-0005). Invocation keeps the
`sendMessage` path so the send stays in the transcript, rendered as a command card
([RQ-0031](../requirements/rq-0031.md)'s card), not prose. **Build gate:** starts only after the
round-three chrome slot lands — its rebuild of Chat/Controls/PlaybookStrip demolishes anything
anchored there earlier. Depends on [ST-0068](st-0068.md) for the stub's re-advertise fixture.

## Acceptance criteria

- [AC-1] Harness-advertised commands appear in the composer's menu beside playbooks, grouped by
  origin, in the harness's own names and descriptions.
- [AC-2] Invoking one sends the text the harness expects (proven by the echo stub) and the
  transcript renders it as a command card.
- [AC-3] A command advertised mid-session appears without restart; a withdrawn one disappears —
  including from an open menu.
