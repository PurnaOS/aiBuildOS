# ST-0069 — Harness commands join the composer

*As an owner, I want what the harness can do listed where I compose — beside my playbooks, in
the harness's own words — not hidden in a chip.*

The transport is done: `available_commands_update` flows bridge → `Controls` cache →
`session:controls`, live and wholesale-replaced. This story is the surface. The composer home
([RQ-0043](../requirements/rq-0043.md)'s `+` menu) now exists as `workspace/Composer.tsx`, and
it gains an origin-grouped Commands section beside its playbooks — grouped the way
`agentControls.ts` groups settings, and by the same discipline: **the grouping and merge logic
lives in a pure module** (`workspace/composerCommands.ts`, tested without jsdom), so the
component only renders what it is handed. The commands themselves come from a session-keyed
`useSyncExternalStore` store (the `toolCall.ts` pattern — never the UI-only zustand store, per
DC-0005). Invocation keeps the `sendMessage` path so the send stays in the transcript, rendered
as a command card ([RQ-0031](../requirements/rq-0031.md)'s card), not prose. Depends on
[ST-0068](st-0068.md) for the stub's re-advertise fixture.

## Acceptance criteria

- [AC-1] Harness-advertised commands appear in the composer's menu beside playbooks, in their
  own section under an origin heading naming the harness — the menu reading the way the agent
  popover reads (Playbooks / Commands — *harness*), never interleaved — in the harness's own
  names and descriptions.
- [AC-2] Invoking one sends the text the harness expects (proven by the echo stub) and the
  transcript renders it as a command card.
- [AC-3] A command advertised mid-session appears without restart; a withdrawn one disappears —
  including from an open menu.
