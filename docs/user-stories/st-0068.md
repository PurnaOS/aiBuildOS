# ST-0068 — The ACP extension carries typed plans and verdicts

*As the application, I want the agent's plan and verdict to arrive as data I validate, not prose
I hope I parsed — where the agent supports it, and unchanged behaviour where it doesn't.*

The DC-0028 mechanism, built at its seams: `AgentSession.open` stops discarding the `initialize`
response and retains `agentCapabilities` (probe already keeps the shape) — extension support is
advertised in its `_meta` per the spec. New CUSTOM names join the bridge's map so extension
payloads reach main whole (known update kinds strip `_meta` today; extension events must forward
intact). A typed plan lands the way plans already land — as draft artifacts, but written through
knowledge-engine `create`/`edit` with `validate()` findings as the reject-back payload, keeping
`derivePlan` the single authority. A typed check verdict is persisted the way the manual walk
already persists one (`last_result`/`last_run`/`last_run_by` through the guarded save), keeping
RQ-0019's exit-code truth untouched. The stub agent grows the extension fixtures — capability
advertisement, conforming payloads, a conform-on-retry case, and the baseline negative control —
and this lane owns **all** stub edits, including ST-0067's permission option and ST-0069's
command re-advertisement.

## Acceptance criteria

- [AC-1] A session with an extension-advertising agent receives plans as schema-validated data;
  a non-conforming payload is rejected back to the agent with the validator's findings.
- [AC-2] Typed check verdicts persist on the record through the guarded save; exit codes remain
  the truth for what ran.
- [AC-3] Capability negotiation happens at initialize via `_meta`; agents that advertise nothing
  get today's behaviour, proven by the stub's baseline mode.
- [AC-4] All extension traffic rides ACP `_meta`/CUSTOM events — no new door, no new IPC channel.
