# ST-0067 — Supervision maps to the harness's permission option

*As an owner choosing how closely to supervise, I want the harness's own permission behaviour to
follow my choice — the same truth on both sides of the ACP wire.*

The plumbing exists end to end (`setConfigOption` in `packages/acp/src/session.ts`,
`session:set-config`, `config_option_update` folding into the `Controls` cache in `sessions.ts`).
What's missing is the mapping and its caller. The mapping is data on the harness record: an
optional field on `HarnessSchema` (level → `{configId, value}`), prefilled from
`HARNESS_PRESETS` — persisted on the record because saved harnesses carry arbitrary ids, so a
preset-id lookup would miss every real one. Applied in `sessions.ts` at session start (the
`supervisionOf` seam) and fanned out to every open session of the project when supervision
changes — the registry gains a project→sessions helper. Depends on [ST-0068](st-0068.md) only
for the stub agent's permission-flavoured config-option fixture (one lane owns all stub edits).
DC-0028's rule holds: config options, never the deprecated modes API.

## Acceptance criteria

- [AC-1] Starting a session applies the supervision level's mapped config option; changing
  supervision mid-session pushes the mapped option to every open session of the project.
- [AC-2] The mapping lives on the harness record as data, prefilled from the shipped presets;
  no harness is special-cased in code.
- [AC-3] A harness with no mapping behaves exactly as today, and the settings surface says the
  level is app-side only.
- [AC-4] A harness-side option change updates what the supervision display shows — never a
  silent disagreement.
