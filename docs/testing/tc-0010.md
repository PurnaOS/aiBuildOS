# TC-0010 — The type profile loads from disk and resolves extends by merging child over parent

Verifies [RQ-0003](../requirements/rq-0003.md) AC-1 and AC-14, covering
[ST-0006](../user-stories/st-0006.md). Runs on Node under Vitest: the resolver against literal type
definitions, the loader against a fixture directory in a temporary location.

Resolution is tested from literals rather than from this repository's own `docs/profile/`, so the
test does not fail when the profile legitimately changes.

## Steps

1. Load a fixture bundle's `profile/` directory containing type definitions, a `README.md` index and
   a manifest carrying `name`/`version`/`formats` and no `type`.
2. Expect the type definitions collected and the index and manifest skipped — neither is reported as
   an error.
3. Expect a type definition with unparseable frontmatter reported as a finding, with the remaining
   definitions still resolved.
4. Resolve a two-level chain — a grandparent, a parent that `extends` it, and a child that `extends`
   the parent — and expect `fields`, `links` and `states` merged along the whole chain.
5. Expect a key the child redefines to hold the child's value, and a key only the parent defines to
   survive.
6. Ask whether the child is its grandparent's type and expect yes; ask about an unrelated type and
   expect no.
7. Ask whether a type the profile does not define matches itself, and expect yes by name equality.
8. Run the `docs:check` CLI against a fixture bundle and expect its output shape, its `bundle/empty`
   guard and its exit code unchanged from before profile loading existed.
9. Validate a bundle with no profile and expect the four pre-existing rules to run and no type-related
   finding to appear.
