# BG-0009 — Killing a check or preview reaches only the shell wrapper, not the work

The first run of CI's Linux job — the 3-OS matrix had never run before — failed five process
tests. Three were real: `killChecks` and the preview's teardown call `child.kill()`, which
signals the direct child only. On macOS that child *is* the work, because bash (macOS's
`/bin/sh`) execs into a single simple command. On Debian-family Linux, `/bin/sh` is dash, which
stays resident as a wrapper — so the kill took the wrapper and orphaned the real process, which
kept the stdio pipes open and the app waiting: a long-running check survived `before-quit`
(RQ-0019#AC-5), and a stopped preview left its server holding the port (RQ-0025). Windows has
the same shape through `cmd.exe /c`. The ceiling was known and marked (`ponytail:` in both
files, DC-0021-era); Linux proved it real.

The other two failures were the tests' own instrument lying: `pgrep -f` invoked through an
`sh -c` wrapper matches the wrapper's command line on Linux and reports a survivor that never
existed — a test fix, not a product bug, corrected in the same change.

## Reproduction

On Linux (or any dash-`/bin/sh` system): start a check whose command runs longer than the app
(`node -e "setTimeout(()=>{},5000)"` behind a `check` fence), quit the app while it runs — the
node process survives `killChecks`. Same with a preview server and `stopPreview`: the port stays
held. CI run 32439403731 (ubuntu-latest) is the original failure.

## What the fix does

One shared reaper (`apps/desktop/src/main/reap.ts`): checks and previews spawn `detached` on
POSIX so the child leads its own process group, and the kill signals the group
(`process.kill(-pid)`); on Windows, `taskkill /T` walks the tree. [TC-0057](../testing/tc-0057.md)
and [TC-0070](../testing/tc-0070.md) are the regression evidence, green on macOS and Linux.
