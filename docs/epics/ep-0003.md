# EP-0003 — Profile-driven validation

Making [`docs/profile/`](../profile/README.md) load-bearing. The type definitions already describe
every constraint this project cares about; nothing reads them. This epic turns the profile from
documentation into the validator's input.

Implements [RQ-0003](../requirements/rq-0003.md).

## Scope

### In scope

- Reading the profile off disk and resolving `extends` into fully merged type definitions.
- Frontmatter rules: the type exists and is concrete, the prefix and directory match it, required and
  enumerated fields hold, the state is in vocabulary, agent-authored artifacts carry `generated`.
- Link rules: the relationship is declared, the target's type is accepted, cardinality holds, and
  relationships marked `cycles: forbid` are acyclic.
- Body rules: required sections are present, acceptance criteria exist and are uniquely numbered, and
  `#AC-n` links resolve.
- Wiring all of it into `bun run docs:check` without changing its output shape or exit code.

### Out of scope

- **State transitions.** The profile declares them; a single commit cannot show what a state was
  before. That needs Git history, which is its own requirement.
- **`[AC-n]` append-only enforcement.** Same reason.
- Gates and gate compositions, CST-based round-trip editing, and the Ajv `json_schema` escape hatch —
  all three reserved by [DC-0009](../decisions/dc-0009.md).
- Surfacing findings in the desktop app. The engine produces them; no story asks for that screen yet.
- Fixing what the new rules find in the existing bundle beyond what it takes to keep `docs:check`
  green.
